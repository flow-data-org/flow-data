# Правила работы с ИИ-агентами (общие для всех репозиториев flow-data-org)

Это центральный документ, он живёт в репозитории `flow-data` (https://github.com/flow-data-org/flow-data). Репозитории подключают его из своего `AGENTS.md` и могут **переопределять отдельные пункты**
(см. раздел 0). Источник идей: `~/.claude/templates/agent-workflow-template.md` (цепочка SDD → TDD → evals, BMAD,
Orca-воркспейсы, экономия токенов), здесь адаптирован под организацию с несколькими репозиториями.

## 0. Как устроено наследование

- Центральные правила — этот файл. Репозиторий подключает его строкой `@../flow-data/docs/agent-workflow.md` в своём `AGENTS.md` (репозитории лежат рядом в рабочей папке; на GitHub — ссылка на этот файл)
  (`CLAUDE.md` содержит одну строку `@AGENTS.md`).
- Всё, что не переопределено, действует как написано здесь.
- Переопределение — раздел **«Переопределения»** в `AGENTS.md` репозитория. Формат: номер пункта центрального
  документа, что меняется и почему. Пример: `§2 Ворота: вместо pytest — проверка ссылок, потому что кода нет`.
- Переопределять нельзя раздел 9 (безопасность): он обязателен везде. Можно только ужесточать.
- Если правило нужно менять во всех репозиториях, правится этот файл, а не копии.

## 1. Принцип: «требование → проверка → изменение»

- Источник истины — спека (`docs/spec/` в репозитории). В `AGENTS.md` — только «как агенту работать».
- Любое изменение идёт цепочкой: **требование → падающий тест или eval → код**. Нет требования — сначала оно.
- Перед реализацией показывается красный прогон, упавший по ожидаемой причине.
- «Готово» = зелёные ворота (раздел 2), а не слова.
- Для репозиториев без кода (документация, курс) «тест» = проверка до и после правки (ссылки, YAML, gitleaks).

## 2. Ворота «готово»

Набор проверок, которые должны быть зелёными, задаёт репозиторий (в переопределениях). Минимум для всех:

```sh
gitleaks git --staged --no-banner   # нет секретов
<линтер/формат/типы/тесты, если есть код>
```

CI обязателен. LLM-проверки только дополняют статические, не заменяют.

## 3. Тесты, evals, трассировка (репозитории с кодом)

- У каждого требования стабильный ID (`FR-001`, `NFR-001`); тест или eval помечается этим ID.
- Скрипт трассировки в CI проверяет, что каждое обязательное требование покрыто.
- Критичное (права, конфиденциальность, лимиты, секреты, запись во внешние системы) проверяется **кодом и юнит-тестом**,
  а не промптом.
- Evals: N прогонов, pass rate. Порог merge: 100% для критичных сценариев, ≥90% для остальных (`epochs=10`);
  при разработке `--epochs 3`.
- Быстрые и тяжёлые тесты разделяются маркерами; тяжёлые (Docker, стенд) — раз перед merge.

## 4. BMAD — только если нужен

По умолчанию не используется. Если подключается: нужен минимум (планирование один раз и цикл `bmad-build` на story),
кастомизация только через `_bmad/custom/*.toml`, лишние скиллы скрываются через `skillOverrides`. Каждый лишний скилл
стоит токенов в каждой сессии.

## 5. Воркспейсы (Orca worktree)

- Одна фича — один воркспейс, имя kebab-case из 2–4 слов; не `test`, `new`, `wip`.
- Создание: `orca worktree create --name <имя> --no-parent`; работу делает **новая сессия агента**, запущенная в нём:
  `orca agent launch --agent claude --worktree path:<путь> --prompt "<задача>"`.
- Главный чекаут — только запуск, merge, чистка и HANDOFF. Разработки там нет.
- Завершение = часть «готово»: commit → merge в `main` → удалить воркспейс и ветку. Если папка игнорируется git
  (вложенные репозитории), перед удалением воркспейса убедиться, что файлы не потеряются.
- Не больше 3 живых воркспейсов (реально 1–2). Одна сессия — одна задача. Push и merge — по просьбе пользователя.

## 6. HANDOFF и короткие сессии

- `docs/stories/HANDOFF.md` (не коммитится): готово, в работе, принятые решения, следующий шаг. Один экран.
- После merge агент предлагает пользователю сделать `/clear` (сам не может) и продолжить по HANDOFF.
- Субагентам — минимальные промпты; большие диффы целиком в контекст не читать.

## 7. Экономия токенов

- Sonnet по умолчанию, в том числе для субагентов и ревьюеров; Opus — для критичного или по просьбе.
- Ревью по размеру: крупное и критичное — полный набор слоёв, мелкое — один слой.
- Мелкие механические правки — без субагентов. Не запускать больше субагентов, чем нужно шагу.
- Эффект оптимизаций проверять измерением (`/usage`, `/context`), а не предполагать.

## 8. Стиль работы с пользователем

- Язык пользователя (по-русски). Коротко: 3–6 строк, один вопрос за раз.
- Сначала короткий план и согласование, затем действия. Не запускать большую работу молча.
- Идти дальше самому; останавливаться на необратимом и внешнем: push, смена видимости репозитория, удаление,
  сторонние сервисы.
- Показывать результат: пути файлов, команды проверки, ссылки.
- Качество важнее скорости для крупных и критичных задач.

## 9. Безопасность (обязательно, не переопределяется)

- Не публиковать API-ключи, токены, пароли, приватные ключи, реальные `.env`.
- Секретные файлы в `.gitignore`; `.env.example` только с тестовыми значениями.
- CI/CD — через GitHub Secrets.
- `pre-commit` с gitleaks в каждом репозитории (`.pre-commit-config.yaml`); в новом клоне: `pre-commit install`.
- Workflow `gitleaks.yml` в каждом репозитории: общий `.github` его не раздаёт.
- Secret Scanning и Push Protection включать, где доступны (публичные репозитории, платный план для приватных).
- Секрет попал в GitHub: **немедленно отозвать и перевыпустить**. Удаление файла ключ безопасным не делает.
- Данные пользователя (имя, почта) не отправлять во внешние сервисы без явного разрешения.

## 10. Чек-лист нового репозитория

1. Имя по схеме: `course-*` (курсы), `product-*` (продукты).
2. `AGENTS.md` с `@../flow-data/docs/agent-workflow.md` и разделом «Переопределения»; `CLAUDE.md` = `@AGENTS.md`.
3. `.gitignore`, `.env.example`, `.gitleaks.toml`, `.github/workflows/gitleaks.yml`, `.pre-commit-config.yaml`.
4. README по шаблону `flow-data/templates/README.template.md`.
5. Автор коммитов: `git config user.name flow_data_admin`, `user.email flowwdata@yandex.ru`.
6. Добавить проект в Orca: `orca repo add --path <путь>`.
7. Защита ветки `main` и включение Secret Scanning там, где доступно.
